# Data sources & tag mapping

All data flows through the **DataHub** (`src/data/data-hub.js`). Widgets bind
to logical datapoint ids; `config/tags.config.js` decides where each value
comes from. This file is the platform's tag map.

## Datapoint definition

```js
'energy.totalUsage': {
  label: 'Total Energy', unit: 'kWh', decimals: 1,
  kind: 'scalar',                       // 'scalar' (default) | 'dataset'
  source:  { type: 'omi', address: 'Energy.TotalUsage' },   // live binding
  sim:     { type: 'wave', min: 530, max: 965, period: '24h', jitter: 22 },
  history: { window: '7d', interval: '10m' },
},
```

Samples delivered to subscribers: `{ value, quality, ts }` with quality
`Good | Uncertain | Bad | Disconnected | Simulated`.

## Data modes

Set by the **Data Mode** widget property (`Auto`/`Live`/`Simulation`) or
`?mode=` URL override in development.

- **simulation** — every datapoint uses its `sim` profile. Header shows the
  amber `SIMULATION` badge.
- **live** — datapoints route to their `source`; datapoints *without* a live
  source fall back to simulation with quality `Simulated` (KPI cards show a
  SIM chip). Disable this fallback with
  `data.simulateUnboundInLive: false` in `config/app.config.js` to show
  unbound points as unavailable instead.

## Source types

### `omi` — AVEVA OMI tags
```js
source: { type: 'omi', address: 'Production.Rate' }
```
Full tag name = **Tag Prefix property** (default `Factory.`) + `address`.
Re-deploy the same CWP against another plant/area by changing the prefix in
the OMI Properties panel — no config edit needed. Subscriptions use the host
postMessage API and are released when no widget needs the tag.

String state tags pass through unparsed; numeric strings are parsed to
numbers. PLC integer state codes are normalized via the state group's
`valueMap` (see [state-and-alarms.md](state-and-alarms.md)).

### `rest` — Historian / MES / SAP / SQL gateways
```js
source: { type: 'rest',
          url: 'https://mes.example.com/api/workorders?line=A',
          intervalMs: 30000,
          path: 'data.items',                  // dot-path into the JSON
          headers: { 'X-Api-Key': '…' } }
```
Generic polling adapter for anything that can expose JSON over HTTP — the
standard integration path for AVEVA Historian's REST API, MES, SAP gateways
and SQL-backed services. Scalar datapoints expect a number at `path`; dataset
datapoints expect an array of row objects. Failures publish quality `Bad` and
keep polling (transient outages self-heal).

### `derived` — computed datapoints (work in every mode)
```js
derived: { op: 'sum',   inputs: ['a', 'b'] }
derived: { op: 'avg' | 'min' | 'max' | 'diff', inputs: [...] }
derived: { op: 'ratio', numerator: 'a', denominator: 'b', scale: 100, clamp: [0, 100] }
derived: { op: 'scale', input: 'a', factor: 1.47, offset: 0 }
```
Inputs resolve through the hub, so derived values follow whatever sources are
active. Quality propagates as the worst input quality.

### `computed` — values produced by platform modules
Marked `computed: true`; published by code via
`SFP.data.computedSource.set(id, value)`. Used for machine state counts
(`machines.count.*`). You rarely add these by hand.

### `simulation` — demo profiles
```js
sim: { type: 'wave', min, max, period: '24h', jitter, phase }  // smooth cycles
sim: { type: 'walk', min, max, step }                          // random walk
sim: { type: 'static', value }
sim: { type: 'dataset', data: [ {...}, ... ] }                 // tables
sim: { type: 'machine', machine: 'M-001', metric: 'state' }    // generated by
                                                               // machines.config.js
```
Datapoints with `history` are backfilled at startup so charts are meaningful
immediately.

## History

```js
history: { window: '7d', interval: '10m' }
```
The hub keeps a bounded ring buffer per datapoint (window/interval samples).
Live updates faster than `interval` refresh the latest slot instead of
appending, so high-frequency tags can't exhaust memory. `time-series` range
buttons and KPI/stat trends read from this buffer. Only datapoints used by
charts or trends need `history`.

## Machine datapoints

`config/machines.config.js` generates `machine.<id>.<metric>` datapoints from
its metric templates (`{id}` is substituted into the OMI address). The machine
registry also publishes fleet counts (`machines.count.running`, `…idle`,
`…maintenance`, `…error`, `…total`).

## Adding a brand-new source type

1. Create `src/data/sources/my-source.js` implementing:
   ```js
   { activate(id, def, publish), deactivate(id, def) }
   ```
   `publish(value, quality, ts)` pushes samples for that datapoint.
2. Register it in `src/app.js`: `hub.registerSource('mytype', new MySource())`.
3. Add a `<script>` tag in `index.html`.
4. Bind datapoints with `source: { type: 'mytype', … }`.

Widgets need no changes — that is the point of the abstraction.
